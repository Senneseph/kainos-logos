## 2. The ψ‴ engine fix (found via the TS port, dps-verified, applied)

Porting Z_rs to TS exposed a defect in the "verified" engine: at t ≈ 41 the
engine's zero location is offset by ~1.03e-4 from the true zero (Z(γ₇) =
−1.6e-4, not ~0). Root cause: `_psi_d3` returned **Re**[alternating com-
plex-step sum]/h³ — an O(h·ψ⁗) near-zero residual (mpmath: 0.0749 where the
true ψ‴ = 2.6253, wrong sign at one p; 35× off). The RS R-term needs the
TRUE ψ‴(p), which the complex-step identity puts in the IMAGINARY part:
S = (ih)³ψ‴(p) − 1.5h⁴ψ⁗(p) + (5/4)ih⁵ψ⁗⁗⁗(p)+… ⇒ ψ‴(p) = −Im[S]/h³.

verbatim copies so the numpy-less docker image can run the engine pieces):

The t < 1e4 remainder is the intrinsic 2-term RS floor (the engine's

## 4. The 2K-drift correction (Day-3 certificate, sharpened)

While certifying γ₁₃₈₀₆₆ I evaluated the Day-3 identity
`2K(T) = (N(T) − main(T) + 1) − arg ζ(½+iT)/π` at T = γ* ± 0.25:
**2K = −2.999999934 (dps-45, 6.6e-8 floor) — an ODD value.** Day-3 had
certified 2K = −2 (even) at 1e5 and 5e5. The drift check (float engine,
exact): on a zero-free interval 2K(T) is NOT constant —

    d/dt [(N − main + 1) − argζ/π] = −(dmain/dt + Ṡ_cont) ≈ −3.0/rad

(main rises at ln(T/2π)/2π ≈ 1.54/rad; the continuous argument rises at
≈ π·1.54/rad; N is flat between zeros). At a simple on-line zero the jump
exactly cancels the interval drift (N steps +1, arg steps +1, wrap
structure preserves evenness mod 2) — so the DAY-3 usage is still valid:
**at each certified height, 2K even (to within its measured dps floor) is
consistent with no off-line zero below that height; odd ⇒ one.** What is
correction is any reading of 2K as a conserved quantity between heights.
The 1e7 update will report 2K at several heights with their floors, and the
off-line certificate of record remains the S-envelope + twin-floor count +
E5 (zero-term-in-tail) when it lands — 2K is a shadow of those, not the
certificate itself. (Recorded; no Day-3 number invalidated: at 1e5/5e5 the
even readings stand as readings.)

## 6. The BLAS-threading stall (engineering, one line that cost three hours)

The two re-walks had "stalled" for ~3.5 h wall / 216 CPU-min. Diagnosis:
`ps` showed TIME slightly exceeding ELAPSED — multithreaded. numpy/OpenBLAS
in this environment spawns a 16-thread pool per small dot (N ≈ 437–1261):
~1–5 ms per Z call of thread-pool overhead, and the two walks competing
for the same cores; meanwhile a direct single-thread timing measured 90–150
µs/call. Killed and re-launched with `OPENBLAS_NUM_THREADS=1
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1`; the first capture-redirect mistake
(re-launch printed to /dev/null) was caught and redone with the proper out-
files. Standing rule for all CPU walk jobs: **single-threaded BLAS + the
output file in the same command line.**
