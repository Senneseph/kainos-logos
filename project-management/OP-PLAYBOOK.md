## House policy: file creation and opaque tokens (STANDING, 2026-08-23)

Owner directive (2026-08-23). Two rules, permanent:

1. **Use the `write` command to create files** (and `edit` for pinpoint
   in-place changes). Do not route file creation through `bash` heredocs /
   `cat >` / `python3 - <<EOF` string-building unless there is an
   exception: the content is (a) generated by a program at runtime, or
   (b) an append to a large file not otherwise being rewritten — and even
   then prefer `read` the file, append in memory, `write` it back whole.
   The `write` tool round-trips UTF-8 byte-correctly (verified 2026-08-23
   for ℓ δ γ → ² ν ≥ H_ℓ). This SUPERSEDES the old "use a heredoc to avoid
   mangle" habit — that habit was specific to board comment payloads (gotcha
   #2), not to ordinary files.
2. **Opaque tokens are written ONCE and read back — never re-derived in
   narration.** A *opaque token* is a long string whose value is frozen
   and whose spelling-out is noise: a domain-coding string (`FLSTSS…`), a
   frozen hash / run-identity, a long pre-reg block, a per-turn script. When
   one must be created: in a SINGLE turn, `write` it to a scratch file
   (`/tmp/<name>.txt`) and do nothing else that turn. In later turns, when
   the token is needed, `read` that file — the file is the single source of
   truth. NEVER re-derive, re-spell, or recompute the string in a visible
   reply; it is a frozen value and re-deriving it is how one-letter slips
   (the D-e6q/v class) get introduced.
3. **Domains get FULL WORD names, not meaningless one-letter codes.**
   The owner rejected opaque one-letter encodings ("you can't spell them
   out because they don't have a MEANING … GIVE THEM A FULL WORD OR NAME,
   you could do it the first time and not go back and forth forever";
   2026-08-23). Anything that names a class of turn/behavior/mode — a
   domain, a check, a state — is named in the per-turn script and the
   prose with the full word (gap, lesson, derived, scaffold-fail, wall,
   conditional, flip, …). A compact letter string is at most a
   **mechanically-derived projection** of the labeled per-turn table
   (computed at freeze/report time by code, e.g. `_turn_domain`), never
   hand-derived and never itself the frozen artifact. The frozen
   artifact is the Labeled table; the letters exist only as an
   audit-friendly hash projection. This eliminates the drift class
   behind D-e6q/D-e6v (hand-spelled domain lines that later turn out to
   disagree with the per-turn script they were supposed to encode).

## Gotchas table (what bit, how to avoid)

1. **`Authorization: Token <t>` → HTTP 401.** The server (and the `op` CLI,
   `op` line ~56) use **Bearer**. Always `Bearer`. An old handoff note said
   "Token" — Bearer is what is verified working (2026-08-21).
2. **Long markdown in a bash heredoc mangles.** `python3 - <<'PYEOF'` with
   ~3 KB of markdown (backticks, quotes, tables) produced
   `unterminated triple-quoted string literal` → payload file never written →
   `curl -d @file` failed with `option -d: error encountered when reading a
   file`. **Reliable pattern:** write a small Python builder with the `write`
   tool (`lines = [...]` joined at runtime, unicode escaped, no very long
   physical lines), run it, *verify the JSON parses*, then `curl -d @file`.
   See "Canonical comment recipe" below.
3. **Comment body must be the RICH-TEXT object**, not a plain string:

   ```json
   {"comment": {"format": "markdown", "raw": "..."}, "public": false}
   ```
   Plain `{"comment": "text"}` does not render (and can 400). **VERIFIED
   HARD 2026-08-28** (S31 close-out): the flat rich-text body is the
   ONLY accepted shape on this instance — `{'activity_type': 'note',
   'properties': {…}}` (wrapped, rich or plain) → 400 "comment is
   missing"; flat + plain string → 400 "comment is invalid"; flat +
   rich-text → 201 `Activity::Comment`. Activities are append-only:
   DELETE /api/v3/activities/{id} → 404 and PATCH of the comment →
   400; a stray probe activity (497 on WP #157, 2026-08-28) is now
   the permanent record of that (superseded in text by activity 498).
4. **`.env` is per-shell.** `source .env` does not persist across bash tool
   calls. Every raw-curl block must start with `cd <repo> && source .env && …`
   (the `op` CLI is exempt — it reads `.env` from the CWD by itself).
5. **`project-management/` is git-IGNORED** (process docs stay local).
   `SESSION-HANDOFF.md` inside it is *tracked* (force-added at Phase 0).
   `git add project-management/SESSION-HANDOFF.md` fails with
   "The following paths are ignored by one of your .gitignore files" and
   **aborts the whole `git add` batch** (exit 1, nothing staged).
   Fix: `git add -f project-management/SESSION-HANDOFF.md` (separately, or
   last). Never add other `project-management/` files without `-f` — and
   only the handoff should ever be tracked there.
6. **Quoting multi-word values:** `status="In review"` (space), `percentdone=100`
   (int). The `op` kv-parser takes everything after `=`, so quotes are only
   for shell word-splitting.
7. **Success is quiet.** `op wp update` prints one line; curl prints nothing
   without `-w`. Always assert: `op` → follow with `op wp get <id>`;
   curl → `-w "HTTP %{http_code}\n"` and expect **201**, then note the
   `Activity::Comment` id from the response body (it becomes the ticket-trail
   reference in sign-off comments).
8. **Never close tickets unilaterally** (standing owner rule): the AI sets
   `In review` 100% + evidence comment; the owner's sign-off closes
   (`status=Closed percentdone=100` + short sign-off comment).

## Canonical recipes (verified 2026-08-21)

### A. Move a ticket to In progress / In review (+ N%)

```bash
cd /home/jsmille/Projects/kainos-logos
./project-management/op wp update <ID> status="In review" percentdone=100
./project-management/op wp get <ID>   # verify — JSON: status is `_embedded.status.name`, percent is `percentageDone`
  # e.g. python3 -c "import json,sys; d=json.load(sys.stdin); print(d['_embedded']['status']['name'], d['percentageDone'])" < <(op wp get <ID>)
```

### B. Post an evidence comment (the recipe that survives long markdown)

```bash
# 1) builder script (via the write tool): /tmp/wp<N>_build.py
#    lines = [ "...short lines...", ]; payload = {"comment":
#    {"format": "markdown", "raw": "\n".join(lines)}, "public": False}
#    -> writes /tmp/wp<N>_comment.json
# 2) run + verify + post, in ONE shell call:
cd /home/jsmille/Projects/kainos-logos && source .env \
  && python3 /tmp/wp<N>_build.py \
  && curl -s -o /tmp/wp<N>_resp.json -w "HTTP %{http_code}\n" \
     -X POST "http://localhost:8080/api/v3/work_packages/<ID>/activities" \
     -H "Authorization: Bearer $OPENPROJECT_ACCESS_TOKEN" \
     -H "Content-Type: application/json" -d @/tmp/wp<N>_comment.json \
  && head -c 160 /tmp/wp<N>_resp.json
# expect: HTTP 201 and {"_type":"Activity::Comment","id":<new id>,...}
```

### C. Close a ticket (sign-off, or delegation)

```bash
cd /home/jsmille/Projects/kainos-logos && source .env
./project-management/op wp update <ID> status=Closed percentdone=100
# + recipe B with a 2-4 line sign-off summary (commit, evidence path, gate)
```

**Governance (2026-08-21):** the owner DELEGATED closing - "you no

### D. Commit the handoff edit (after any board work)

```bash

git commit -m "Step N (...): ..."
```
